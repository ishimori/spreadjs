## 目的

業務アプリが薄い点線の横罫線を一括指定でき、行追加・削除後も同じ見た目を維持できるようにする。最初の利用先は松下の生産納期（管理表①）。

2026-09-06の実装開始指示によりSDK実装・配布物準備まで実施する。松下への適用はSDK完成後にconsumer側で行う。

## 背景・課題

- 松下 `C:/repo/matsushita-production-management` の `#/production-orders` は24列の明細表。consumer DD-025で列の配色・縦区切り・No〜品名の固定を改善したが、横に行を追う補助として各行の下に点線を入れたい。
- [DD-047](../archived/DD/DD-047_行列の区切り罫線.md)で `rowBorders` / `columnBorders` を提供済み。現行 `GridBorder` は `color` / `width` の実線のみで、renderの `border-layer.ts` は帯を `fillRect` で描く。
- `rowBorders` はRowIdごとのmount時固定設定。新規行へ自動コピーされない。consumerが全行分のRecordを作り直す方式では、Reactの再mountで編集中の状態・選択・スクロールを失う可能性がある。
- `base-layer.ts` は既定の実線格子を描いた後に装飾罫線を重ねる。点線だけを上描きすると隙間に既定実線が残り、点線にならない。
- 表本体はCanvasであり、consumerのCSS指定だけではセル境界の線種を変更できない。

参照元: consumerの `src/client/pages/ProductionOrdersGrid.tsx` / `src/client/lib/production-order-appearance.ts` / `doc/DD/DD-025_生産納期の視認性改善.md`。業務名や日付判定をSDKに持ち込まない。

## 検討内容

以下の推奨案を採用。パターンの数値・具体的検証は [確定シナリオ](DD-048/e2e-scenarios.md) に記録する。

| # | 論点 | 推奨案・確定条件 |
|---|------|------------------|
| 1 | 線種 | `GridBorder.style?: 'solid' \| 'dotted' \| 'dashed'` を追加。省略は従来の実線。行・列の個別罫線で同じ型を使う |
| 2 | 全行共通の横罫線 | `defaultRowBorder?: GridBorder` をgrid/reactへ追加。現存する各データ行の下端（最終行を含む）へ適用。先頭行の上端・見出し・行番号帯・データ外の空白へは延長しない。0行は描かない |
| 3 | 個別指定との優先順位 | 隣接行の明示的なbottom/topをDD-047の規則（太い線→同幅なら下行top）で解決。明示線がない境界だけ共通線を使う。共通線より細い明示線も優先する |
| 4 | 既定格子線との合成 | 点線・破線を指定した境界だけ既定の実線を抑止する。白塗りで消さず、列背景・行背景・値ベース背景を保つ。無指定や既存の実線設定の表示は維持 |
| 5 | 周期・DPR | 線幅に応じたSDK既定の点間隔／破線長を採用し、自由なdash配列は提供しない。点線と破線が区別できる形状・最小device幅・位相基準をPhase 1で数値化。固定境界で二重描画せず、再描画で周期がちらつかない |
| 6 | 行の増減 | 個別RowIdを列挙せず現在の行境界で共通線を解決。ローカル／リモートの挿入・削除、セル編集のUndo/Redo、standaloneのsetData後も再mountなしで適用 |
| 7 | ライフサイクル | 表示専用・mount時固定。Reactは新propとstyleを正準化比較に含める。同値設定で再mountしない。style省略とsolid明示も同値として扱う案 |
| 8 | 不正値・既存契約 | 未知style・不正な共通線は既存の `border-config-invalid` でfail-fast。幅・色・未知IDの契約、明示線同士の競合と交点の優先順、縦境界での文字overflow停止はDD-047を継承 |

### consumerの利用イメージ（API案）

```tsx
<NanairoSheetView
  defaultRowBorder={{ color: '#cbd5e1', width: 1, style: 'dotted' }}
  columnBorders={columnBorders}
  columnBackgrounds={columnBackgrounds}
  // その他の既存props
/>
```

## 決定事項

- 対象は点線・破線と全行共通の横罫線。線種・共通設定とも未指定なら既存動作を維持する。
- 上表の1〜8を採用。線幅はw=max(1, round(width×DPR)) device px。dottedは四角い点w＋隙間2w、dashedは線長4w＋隙間2w。長軸の位相原点は横線がデータ領域左端、縦線がデータ領域上端（device整数）。スクロールやpaneごとにリセットせず、固定境界も1回だけ描く。既存契約は [DD-047の公開契約](../archived/DD/DD-047/contract.md) を参照する。
- coreの文書・protocol・snapshot・保存値・コピーTSVへ装飾を入れない。依存を追加せず、grid/reactの公開APIを通して提供する。
- 対象外: 任意セル範囲の囲み、罫線の編集UI・保存／共同編集、Excel罫線入出力、動的setter、全列共通の縦罫線、任意dash配列、consumer固有の業務条件。
- 既存の「罫線指定で文字overflowを止める」契約は線種に依存させない。選択枠・Presence・入力UIは罫線より前面に維持する。

## 検証シナリオ案

- S1: 24列の明細表で共通点線を指定 → 淡い列背景・空セルを含む全行の下端に途切れた点線。実線の補助線は隙間に出ない。無指定との比較も取得する。
- S2: 個別の太い実線、点線／破線、固定行列、折返し行を併用 → スクロール・リサイズ・DPR変更後も線種・競合・clipが正しい。0行／1行／最終境界も確認する。
- S3: 共同編集の2画面で行挿入・削除、セル編集のUndo/Redo・コピー・選択を行う → 両画面の新規行にも点線が付き、値・接続・選択の既存契約を維持する。
- S4: tarballだけの独立consumerでgrid mount／Reactの両経路、standalone／collaborationを確認 → 新propの型が解決し、setData・追加行に共通線が反映される。同値のReact再描画はdraftを保持する。

## Manual Gate

- 約5分: 松下①相当の例を表示し、実機の拡大率で点線が強すぎず、横方向に行を追えることを確認する。人手確認未実施の場合は、その視認性の未確認範囲をクローズ時に `既知の未保証境界` へ記録する。
