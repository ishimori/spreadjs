## 目的

ReadyCrew RC4（行単位の部分更新・Undo を消さない再注入）・RC13（`onCellCommit` 内で `setData` された際に Undo へ残る幽霊エントリの解消）を実装する。

## 背景・課題

- RC4 現状: `setData`（`mount-controller.ts:3121-3144`、該当3126-3128）は文書を丸ごと差し替え、直後に `undoCtrl.clear()` で Undo 履歴を全消去する。差分のみ当てる部分更新経路は無い
- RC13 現状: コミット経路（`mount-controller.ts:1655-1683`、該当1677-1681）は「`captureUndoPatches`（逆値キャプチャ）→ `submitToBackend`（**単独モードは内部で `cell-commit` を同期発火**）→ `recordUndoEntry`」の順。consumer の `onCellCommit` ハンドラが同期的に `setData`（＝`undoCtrl.clear()`）を呼ぶと、その**後**に `recordUndoEntry` が実行され、消去済みの Undo スタックへ幽霊エントリが積まれる
- 親 DD-052 決定:
  - 論点6 RC4 (a): `ref.setRows(rows)`（RowId で置換・追加し、置換セルに触れない Undo を残す。差し替えの意図が API に出る）
  - 論点8 RC13: 子DD-052-4（本DD）で原因を確認のうえ決定

## 検討内容（RC13 原因確認）

現行コード（背景の引用）から、原因は「`recordUndoEntry` が `submitToBackend` の**戻り値（id）に依存**しており、`submitToBackend` 内部で consumer コールバックが同期発火した後でなければ呼べない」という依存関係にある。対処は次の2案:

| 案 | 内容 | 評価 |
|---|---|---|
| (a) 通知を後段へ切り出す | `submitToBackend` を「適用して id を得る」段階と「`cell-commit` を発火する」段階に分離し、両者の間で `recordUndoEntry` を呼ぶ（発火は最後） | consumer コールバックが同期的に何をしても、Undo 記録は必ずその**前**に完了しているため、`setData` が呼ばれれば `undoCtrl.clear()` が幽霊エントリごと正しく消去する。二重防衛構造（入口ガード＋絶対防衛線）はそのまま維持できる |
| (b) `setData` 時に記録予定の Undo も破棄 | `recordUndoEntry` を現状の順序のまま残し、`setData` 側で「直前に発火した commit の Undo」を判定して取り消す | 「直前」の判定が脆く、非同期タイミングやネストしたコミットで誤判定しうる |

**採用: (a) の意図を、実装時に判明したより単純な形で実現**。`recordUndoEntry` の standalone 分岐（`mount-controller.ts:1785-1788`）を実読すると、`submitToBackend` の戻り値 `id` に**依存していない**（`backend.session.committedDocument` の revision だけで完結）ことが分かった。したがって `submitToBackend` 自体を分離する必要はなく、`StandaloneSession` に「setCells 適用直後・`onCellCommit` 通知の前」に発火する `beforeCellCommit` フックを追加し、そこで Undo 記録を完了させる方が変更範囲が小さい（`submitToBackend`・`submitCompensation`（Undo/Redo 補償）の2呼び出し元を両方とも無改修で保てる）。

## 決定事項

- RC4: `GridInstance` に `setRows(rows: readonly GridStandaloneRow[]): void` を追加（**standalone 専用**。共同編集モードは `setData` と同様 no-op＋診断）。指定された RowId のうち既存行は `cells` で言及した列だけ現在値と比較し、**値が変わったセルだけ**を SetCells として適用する（同値セルは Undo 対象に入れない）。未知の RowId は新規行として**末尾へ**挿入する。**言及しなかった行は完全に不可侵**（削除もしない＝「増減」ではなく「置換・追加」のみに決定を絞った。行削除が要る場合は既存の `deleteRows` を別途使う）。新規行の挿入自体は既存の `insertRows` と同じく Undo/Redo 対象外（本コードベースの既知の制約で、`setRows` 独自の制約ではない）。`readOnlyColumns` は行データで明示した行だけ置き換え、省略した行は既存指定を保つ。readOnly（列・行・セル）は `setData` と同様にバイパスする（プログラム的な再注入のため）。`setData` と同様、変更は `cell-commit` を発火しない（consumer 自身のデータを再度 consumer へ通知するエコーを避ける）
- RC13: `StandaloneSession` に `beforeCellCommit` フックを追加し、`submitLocalOperation` 内で setCells 適用直後・`onCellCommit` 通知の**前**に同期発火させる。`mount-controller.ts` はこのフックで `recordStandaloneUndoEntry`（`recordUndoEntry` の standalone 専用部分を分離した新関数）を呼ぶ。`submitSetCells` は捕捉した逆値パッチを一時変数 `pendingStandaloneUndoPatches` へ置いてから `submitToBackend` を呼び、フックがそれを消費する（readOnly 等で `submitLocalOperation` に到達しなかった場合は `submitSetCells` 側で確実に破棄し次回へ漏らさない）。Undo/Redo 補償（`submitCompensation`）はこのフックの対象外のまま無改修（そもそも新規 Undo エントリを積まない経路のため副作用なし）
