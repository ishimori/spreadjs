## 目的

ReadyCrew RC4（行単位の部分更新・Undo を消さない再注入）・RC13（`onCellCommit` 内で `setData` された際に Undo へ残る幽霊エントリの解消）を実装する。

## 背景・課題

- RC4 現状: `setData`（`mount-controller.ts:3121-3144`、該当3126-3128）は文書を丸ごと差し替え、直後に `undoCtrl.clear()` で Undo 履歴を全消去する。差分のみ当てる部分更新経路は無い
- RC13 現状: コミット経路（`mount-controller.ts:1655-1683`、該当1677-1681）は「`captureUndoPatches`（逆値キャプチャ）→ `submitToBackend`（**単独モードは内部で `cell-commit` を同期発火**）→ `recordUndoEntry`」の順。consumer の `onCellCommit` ハンドラが同期的に `setData`（＝`undoCtrl.clear()`）を呼ぶと、その**後**に `recordUndoEntry` が実行され、消去済みの Undo スタックへ幽霊エントリが積まれる
- 親 DD-052 決定:
  - 論点6 RC4 (a): `ref.setRows(rows)`（RowId で置換・追加し、置換セルに触れない Undo を残す。差し替えの意図が API に出る）
  - 論点8 RC13: 子DD-052-4（本DD）で原因を確認のうえ決定

## 検討内容（RC13 原因確認）

現行コード（背景の引用）から、原因は「`recordUndoEntry` が `submitToBackend` の**戻り値（id）に依存**しており、`submitToBackend` 内部で consumer コールバックが同期発火した後でなければ呼べない」という依存関係にある。対処は次の2案:

| 案 | 内容 | 評価 |
|---|---|---|
| (a) 通知を後段へ切り出す | `submitToBackend` を「適用して id を得る」段階と「`cell-commit` を発火する」段階に分離し、両者の間で `recordUndoEntry` を呼ぶ（発火は最後） | consumer コールバックが同期的に何をしても、Undo 記録は必ずその**前**に完了しているため、`setData` が呼ばれれば `undoCtrl.clear()` が幽霊エントリごと正しく消去する。二重防衛構造（入口ガード＋絶対防衛線）はそのまま維持できる |
| (b) `setData` 時に記録予定の Undo も破棄 | `recordUndoEntry` を現状の順序のまま残し、`setData` 側で「直前に発火した commit の Undo」を判定して取り消す | 「直前」の判定が脆く、非同期タイミングやネストしたコミットで誤判定しうる |

**採用: (a)**。`submitToBackend` の内部を「適用・id確定」と「`cell-commit` 通知」に分離し、`recordUndoEntry` を通知より前に呼ぶ。

## 決定事項

- RC4: `GridInstance` に `setRows(rows: readonly GridStandaloneRow[]): void` を追加。指定された RowId の行のみを対象に、現在値との差分をセル単位の Operation（SetCells）＋行の増減（insert/delete）として適用し、既存のコミット経路（Undo 記録を含む）をそのまま通す。触れていない行・セルの既存 Undo 履歴は保持される
- RC13: `submitToBackend` を「適用して id を確定する」処理と「`cell-commit` を consumer へ通知する」処理に分離し、`recordUndoEntry` を通知の**前**に実行する。これにより consumer が `onCellCommit` 内で `setData` を呼んでも、その時点で Undo スタックには幽霊エントリが残らない
