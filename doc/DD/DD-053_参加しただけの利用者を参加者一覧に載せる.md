## 目的

consumer（広島空港 予算管理モック W-04）で、**セルを選ばずに表を開いただけの利用者**も、他の利用者の参加者一覧（DD-049 H5 の `presence` イベント／`presences()`）に載るようにする。
あわせて、consumer が入れている「参加時に自動でセルを選ぶ」つなぎを不要にする。

## 背景・課題

- 要件の正本: 広島リポ `doc/archived/DD/DD-005/sdk-requirements.md` **H10**（2026-09-12 追加）。乖離したらメモ側が勝つ（DD-035 と同運用）
- 発見の経緯: 広島 DD-005-3（`doc/archived/DD/DD-005-3_SDK更新の取り込み.md` ログ）で alpha.7 の参加者一覧を画面に出したところ、2 ウィンドウを開いても互いの帯に相手が出ず、E2E が落ちた
- 現状（2026-09-12・alpha.7〔`882a56d`〕のソース）:

| # | 箇所 | 挙動 |
|---|------|------|
| 1 | `packages/server/src/room.ts:104-105` | join は userId/displayName を持たないので、他者への `presenceDelta` は**最初の presence メッセージを受けたとき**に配る |
| 2 | `packages/server/src/presence.ts:117-126` | `snapshot()`（後から参加した人へ返す一覧）は、presence を 1 回以上送った接続だけを含む |
| 3 | `packages/grid/src/ime-editing-session.ts:179-190`・`mount-controller.ts:2781-2789` | grid が presence を送るのは activeCell／editingCell が**変わったとき**だけ。mount 直後は送らない |
| 4 | `packages/collab/src/session.ts:782` | 再接続時は直前の presence を送り直す（1 度も送っていなければ送らない） |

  → 1〜3 が重なり、**選択セルを動かしていない接続は、他者の `presences()` にも名前タグにも出ない**。
- DD-049 の契約 §4 は `presence` の契機に「他者の参加」を挙げているが、E2E（`apps/playground/e2e/remote-change.spec.ts:59` 以降）は
  **B がセルを選んでから** A の一覧に B が載ることを確かめており、「参加しただけ」の場合は検証されていない
- 名前タグの描画は、選択セルの無い presence を既に飛ばす（`packages/grid/src/presence-adapter.ts:43-46`）。一覧に載せても枠は描かれない
- consumer のつなぎと、その代償（広島 `mock/src/views/CoEditSheet.tsx` の presence 処理）:
  自分の `presence` イベントで自分の activeCell が null なら `setActiveCell` で入力セルを選ぶ。
  ただし `setActiveCell` は未知の行を無視し（`mount-controller.ts:584-590`・診断は既定で無出力）、今ある行を知る公開 API も無いため、
  先頭行が削除されていると空振りする（広島 Codex P2）。候補行を下から順に全部選んで回避している
- 無操作の利用者が TTL で消える心配は無い（heartbeat が `touch` する）。閉じた接続は ws `close` で即時に消える（広島の実測 12〜278ms）

### 重大な副産物の発見（協議の上、テストの seed 差し替えで対応・根本修正は別DD）

本DDの変更（welcome/reconnect のたびに presence を送る＝メッセージ量が微増）が、`tests/invariants/collab/reconnect-fault.invariant.test.ts` の固定 seed=1,234,567（`injectClientToServer:true` の D27 経路）を
`InProcessHub.deliverAll: message storm`（`operationRejected` が線形に際限なく増え続け 100,000 steps の安全上限で強制停止）で落とすようになった。

**原因調査**: `InProcessHub.deliverNext()` の delay（reorder）ロールは全メッセージ種別に対して毎回シード付き PRNG を1回消費する（`presence`/`presenceDelta` 自体は drop/duplicate 注入の対象外だが、delay 判定の RNG 消費からは除外されていない）。本DDが presence 送信を1〜2通増やしたことで、以降の全フォールト判定に使う乱数列が1ステップずれ、**たまたまこの特定 seed が「衝突しやすい」乱数列を引くようになった**。

実際に落ちているのは `session.ts` の `handleRejected`（`client-sequence-violation` 分岐）で、再送がさらに violation を生み再送するケースが一部のフォールト系列で収束しない、**本DDとは無関係の既存の潜在バグ**。証拠: 本DD適用前のコードのまま、同じ config（`injectClientToServer:true`・他パラメータ同一）で seed だけ 1〜40 を振ったところ **40件中10件（25%）が同じ message storm で落ちた**（seed=2,7,8,27,28,31,32,38,39,40）。既存テストはこの config に対し seed=909,090 と 1,234,567 の2点しか試しておらず、たまたま両方とも「安全な」seed を引いていただけで、収束保証自体は元々担保されていなかった。

コード自体に「client-sequence 完全再整列は未実装」という既知境界の注記があり（`inprocess-transport.ts` コンストラクタのコメント・D27 deferred 境界）、この節はその既知境界の症状の一つと考えられる。

**対応**: 本DDの範囲では seed を 1,234,568 へ差し替え、上記調査結果をテストのコメントに記録するに留めた（`session.ts` 側の resend/violation ロジックへは触れていない＝本DDの Risk Class B を維持）。**client-sequence 完全再整列の頑健性改善は別途 DD として起票が必要**（Risk Class A 相当・Sequencer/ClientSession の protocol level 変更を伴いうる）。ユーザーへ報告済み。
