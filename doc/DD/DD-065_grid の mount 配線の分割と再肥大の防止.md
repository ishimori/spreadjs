## 目的

grid の mount 配線（`packages/grid/src/mount-controller.ts`）を機能ごとのファイルへ分け、機能どうしのつながりを明示的な受け渡しに変える。あわせて、ファイルと関数が再び肥大しないよう lint で止める。挙動・公開 API・protocol は変えない。

狙いは次の 2 つ。

- 機能を 1 つ足すときに読む量と、機能間の干渉の見落としを減らす
- 配線の振る舞い（キー入力の優先順位、候補欄と日付の開閉条件、読み取り専用の抑止など）を、grid 全体を mount せずに単体テストで確かめられるようにする（今は E2E でしか確かめられない）

## 背景・課題

計測の詳細と根拠は `DD-065/diagnosis.md`（2026-11-08・コミット 85018dc 時点）。

- SDK の骨格は健全（パッケージ間の依存方向を lint で強制・循環 import 0・`any`／`@ts-ignore`／TODO 0）。負債は mount-controller.ts 1 ファイルに集中している
- 4,533 行（7/14 の作成時は 623 行）。関数 `createGridController` 1 つが 4,317 行あり、その中の 62 個の `let` を全機能が共有する
- 7/14 以降に SDK のソースを変えたコミット 72 件のうち 53 件がこのファイルを触る。DD-064（セルの結合）だけで +314 行、キー入力ハンドラ `interceptKeydown` の循環的複雑度が 51→62
- 機能どうしは、後から代入する関数の入れ物（`openSelectForActive` など 9 個）でつながっている。キー入力の優先順位は 1 つのハンドラの if の並びで決まり、コメント同士で「最優先」が食い違っている
- vitest には実物の mount-controller を実行するテストが無い（React の jsdom テストは grid を mock している）。配線を確かめられるのは E2E だけで、E2E が通らない経路（例: flush を待っている最中の `destroy()`）は壊れても気づけない
- Codex の指摘番号つきの修正跡が 41 か所あり、タイミングと機能間の干渉が中心。DD-064 の Codex 指摘 4 件のうち 2 件（変換中の結合・開いた候補欄）も同じ種類

## 検討内容

| # | 論点 | 推奨案 |
|---|---|---|
| 1 | 範囲 | mount-controller.ts の分割と、再肥大を止めるガード。1,000 行を超えるほかの 3 ファイル（`render/src/base-layer.ts`・`server-hono/src/server.ts`・`collab/src/session.ts`）は分けず、ガードの baseline に入れて増加だけ止める（server.ts と session.ts は関数・メソッドに分かれていて共有の可変状態が無い。base-layer.ts は次の候補） |
| 2 | 共有状態の持ち方と生成の手順 | 機能ごとに状態を持つ部品にする（`createXxx(ctx)` が自分の状態を内側に持ち、ほかの機能には小さな操作だけを返す）。共有 context には複数の機能が本当に使う状態だけを置く。全状態を 1 つの state オブジェクトへ移す案は、絡みを移すだけなので採らない。class 化は、この SDK の factory 関数の書き方とそろわないので採らない。部品どうしが互いを呼ぶ所（diagnosis §4 の相互依存）は生成と結線を分け、生成時に値を固定せず、結線の段階で操作を渡すか最新値を読む getter で渡す。組み立ては「生成 → 結線 → `backend.start()`」の順を 1 か所に書く |
| 3 | キー入力の優先順位 | 判定を部品ごとのハンドラにし、優先順位は 1 か所の配列に並べる。順序は今のコードのまま（diagnosis §2 の 1〜8）。各ハンドラの結果は「消費して止める」「処理したうえで流す」（Escape の範囲解除）「該当しない」の 3 種類を区別する。各部品が優先度の数字で登録する案は、順序が散らばるので採らない |
| 4 | 分け目 | diagnosis §5 の 9 区画（キー入力の裁定・候補欄・日付カレンダー・ポインター・読み取り専用・起動と 2 モード・編集の結線と命令・E2E 用の口・描画）。ファイル名と最終の分け方は実装時に決めてよい（受け入れ基準を満たすこと） |
| 5 | ガードの方式 | 自前のラチェット検査を `npm run lint` に足す（CI の checks ジョブで走る）。閾値を超える既存の違反は baseline に記録し、値の増加を失敗にする。比較元は変更前の baseline（ローカルは HEAD、CI は push 前のコミット、PR ならベース）で、`baseline.json` を手で書き換えても値の増加と項目の追加を検出する。増加・追加を通すのは、その項目に DD 番号と理由が書かれ、その DD が存在する場合だけ（DD のログにも同じ理由を 1 行残す）。ESLint の `max-lines`・`complexity` と一括抑制（suppressions）は、違反済みのファイル・関数がさらに伸びても件数が変わらず検出できないので採らない |
| 6 | 閾値と目標 | ファイル 1,000 行・関数の循環的複雑度 30。関数の行数は見ない（150 行を超える関数 18 個の大半が、部品全体を返す factory にあたる）。対象は `packages/*/src` のテスト以外。mount-controller.ts の目標は閾値と同じ 1,000 行以下（baseline から外れる）。⑨ 描画まで切り出す前提の見積もり（diagnosis §5）。初期の違反はファイル 4・関数 4（diagnosis §6） |
| 7 | テストの置き場所 | 配線の振る舞いは、切り出した部品の単体テストで確かめる。部品どうしの結線は、実物を mount する E2E で確かめる（React の jsdom テストは grid を mock していて実物を通らない）。今後の機能 DD もこの置き場所に従う（AGENTS.md に書く）。既存の DD 番号つきテストファイル（`*.dd035.test.ts` など）の整理はしない |
| 8 | 配布 | 単独の配布はしない。次の配布に入れ、CHANGELOG に「内部構造の変更（公開 API・挙動の変更なし）」と 1 行書く |

### 守ること（全論点共通）

- 公開 API・イベントの発火順・イベントリスナーの登録順・rAF と microtask のタイミングを変えない（リスナーの登録順はハンドラの実行順を決める）
- 切り出す前に、その区画を守るテストを確かめる。区画ごとに対応する E2E spec と単体テストを表にし、どれにも守られていない経路は、切り出す前にテストを足す（今の挙動を固定してから動かす）
- 各部品は破棄の操作を持ち、組み立ての `destroy()` が今と同じ順で呼ぶ（判定タイマーの取消・flush の待ちの解決・リスナーの解除・DOM の除去）。再 mount で漏らさない。E2E 用の口（test-support 経由の introspection）の形を保つ
- 既存テストの期待値を書き換えない。書き換えが要るなら挙動が変わっているので、止めて原因を調べる
- 1 区画ずつ、単独でコミットでき、テストが通る状態で終える（機能 DD と交互に進められるようにする）

### 対象外

- base-layer.ts・server.ts・session.ts の分割（ガードで増加だけ止める）
- DD 番号つきテストファイルの整理、playground の `main.ts` と `standalone-main.ts` の重複
- 挙動の変更・不具合の修正（分割中に見つけたら別 DD）
