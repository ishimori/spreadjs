## 目的

1 セルの確定・貼り付け・範囲の消去・Undo・行の挿入と削除にかかる時間を、表の大きさ（空でないセルの数）に比例させない。
180 列 × 5,000〜11,000 行で入力確定 50 ms 未満（計画書 §21・DD-070-1 の目標）に戻す。

## 背景・課題

- DD-070-1 の計測（180 列・headless Chromium）: 1 セルの確定が 5,000 行で 178 ms・11,000 行で 402 ms・50,000 行の全部埋まりで 1,595 ms。100 万セルあたり約 180 ms
- 原因は core の `applyOperation`（`packages/core/src/apply.ts`）が「入力の文書を壊さない」ために操作のたびに `cloneDocument` で文書を丸ごと深く複製すること（全セルの CellRecord・CellScalar・全行の RowMeta）
- 同じ関数を単独モードの確定・共同編集の楽観適用と再ベース・サーバーの sequencer が使う。サーバーは操作を 1 件ずつ順に処理するため、大きい表を数人で編集すると互いの操作が待たされる

## 決定事項

- 2026-11-20（提案どおり・ユーザー承認）:
  1. `applyOperation` の「入力の文書を壊さない」約束は保つ。呼び出し側（standalone・collab・server）は変えない
  2. 複製を構造共有にする: CellStore はまとまり（chunk・256 行）と行の配列を共有し、書き換えるときに書き換えるまとまりと行だけを写す（copy-on-write）。行の並び（rowOrder）と行の情報（rowMeta）も共有し、行の挿入・削除のときだけ写す
  3. 共有するため、CellRecord・CellScalar・RowMeta のオブジェクトはその場で書き換えない（差し替える）。core の削除（tombstone）をその場の書き換えから差し替えに改める
  4. 公開の `cloneDocument`・`CellStore.clone()` は今までどおり完全な深い複製のまま（利用側のテストと約束を変えない）。構造共有の複製は新しい `forkDocument`・`CellStore.fork()` で、core の適用だけが使う
  5. 計測をやり直して DD-070-1 の E2E の入力確定を判定に戻す（`COMMIT_KNOWN_SLOW = false`）
- 2026-11-20（Codex の指摘で決めた細目）:
  6. 共有する構造は型でも読み取り専用にする（`SheetDocument.rowOrder: readonly RowId[]`・`rowMeta: ReadonlyMap<RowId, Readonly<RowMeta>>`・`CellRecord`・`CellScalar` の各項目を readonly）。書くのは core の適用と collab の巻き戻し（`applyInverseSeed`）だけで、`writableRowOrder` / `writableRowMeta` を通す
  7. 行の並び・行の情報は「書いてよい入れ物」（作った・写したもの）を記録し、記録に無いものは書く前に写す（知らないものは写す側に倒す）。記録は `globalThis` に 1 つ（`Symbol.for` のキー）置き、core のモジュールが二重に読み込まれても同じ記録を見る
  8. 直列化（`serializeDocument`）と復元（`deserializeDocument`）はセルの値を写す（スナップショットと文書がセルの値を共有しない）
  9. fork の費用は O(割り当て済みのチャンクの数)＝slot の数 / 256（5 万行で約 200）。チャンクの索引の Map は毎回写す（空でないセルの数・列の数には比例しない。索引まで経路だけ写す作りにはしない）

- 実装をコミット（a4393be）し、Codex high にレビューを依頼（`DD-070-10/codex-review-result.md`）
- Codex の指摘（6 件・すべて妥当と判断して採用。4 は作りを変えず費用の約束を明記）:
  1. P1: `serializeDocument` がセルの値を参照のまま返す。古いスナップショットの値を書き換えると、今の文書のセルまで変わる（以前は次の適用の深い複製で参照が切れていた）→ 直列化・復元の境界で値を写す（決定 8）
  2. P2: 共有の記録がモジュールごとの WeakSet で、core が二重に読み込まれると、片方の適用の結果をもう片方が replay して元の文書の行の並びを変える → 記録を「書いてよい入れ物」に改めて、globalThis に 1 つ置く（決定 7）。直す前の作りで失敗するテストを足した（`vi.resetModules` で 2 つ目の core を読み込む）
  3. P2: 読む側（例: `ClientSession.viewDocument.rowOrder.reverse()`）が共有中の配列・Map を書き換えられる → 型を読み取り専用にした（決定 6）。今の SDK に、そうして書き換える経路は無い（型検査で確かめた）
  4. P2: fork のたびにチャンクの索引の Map を写すので、O(チャンクの数) → 作りは変えず、費用の約束をコメントと決定 9 に書いた。チャンクの数は slot の数 / 256 で、空でないセルが疎な表でも 5 万行で約 200
  5. P2: 文書の木のテストが正準形（blank のレコードと削除した行のセルを除く）で比べ、最後にだけ照合していた → 保存の形（`serializeDocument`）・slot・maxSlot で比べ、毎回すべての文書を照合する
  6. P3: ストアの比較の `approxMemoryBytes` が空のチャンクの残り方で深い複製と違いうる → 論理の中身と件数で比べ、文字数の計上は「残りがチャンクの分の倍数」で別に確かめる
- テストが漏れを検出できるかを、直す前の作りに一時的に戻して確かめた: 記録をモジュールごとにする → 二重読み込みのテストが失敗。直列化で値を写さない → スナップショットのテストが失敗。fork で共有の印を外さない（行の並び・行）→ 無作為の木のテストが 7 件・6 件失敗
- 修正の後の検証: typecheck・consumer-strict・lint（size: session.ts は baseline の 1,006 行のまま）・単体 1,852 件（公開 .d.ts の snapshot を含む）・build が成功
- E2E 全 65 本（修正の後）: row-view-collab の AC1 が 1 回失敗（3 回の繰り返しでも 1 回）。A の確定が B に届いた直後に A で Ctrl+Z を押すが、Undo は自分の操作が未確定の間は効かない（undo-stack・意図どおり）。B に届いた時点で A が自分の ACK を処理済みとは限らない、テストの待ち方の競合。確定が速くなって表に出た → undo-redo-collab と同じく A の pendingCount が 0 になるのを待ってから押す。5 回の繰り返しで 45 件成功。ほかの 346 件は成功（zz-rm-database-perf の入力確定 1.8〜2.6 ms）
