## 目的

DD-070-8 の `setRowView`・`visibleRowIds` が共同編集モードでも決定事項どおりに動くことを確かめる。並べ替え・絞り込みは参加者ごと（view-local）で、他の参加者の画面と文書は変えない。

## 背景・課題

- DD-070-8 は単独モードで作って確かめた。行の Axis と再ベースは両モード共通の部品だが、共同編集モードには単独に無い経路がある: 他の参加者の行の挿入・削除・値の変更の受信、自分の操作がサーバーに拒否されたときの巻き戻し（`rebuildView`）、再接続のときの bootstrap（文書の丸ごとの入れ替え）、他の参加者の枠（presence）
- 親 DD-070 の判断: 共同編集で工数が大きく増えると分かったら、そこで止めて単独のみにする

## 決定事項

- 2026-11-20（親 DD-070・DD-070-8 の決定事項をそのまま両モードに広げる）:
  1. 並びは参加者ごと（view-local）。ある参加者の `setRowView` は他の参加者の画面・文書・Undo を変えない
  2. 他の参加者が挿した行は「呼んだ後にできた行」（DD-070-8 決定 3）: 文書の並びで一つ前の見えている行のすぐ後に出る。他の参加者が消した行は並びから抜ける（選択中なら近くの見えている行へ）
  3. 他の参加者が隠れている行の値を変えても画面には出ない（`getRows` では読める）。見えている行の値が変わっても並び直さない（一度きりの並び）
  4. 自分の操作がサーバーに拒否されて巻き戻ったとき: 巻き戻しで消えた行（拒否された挿入）は並びから抜け、巻き戻しで戻った行（拒否された削除）は元の並びの位置に戻る（呼んだ時点にあった行なら並びに残っているため）
  5. 再接続の bootstrap で文書が入れ替わっても、同じ行 ID の行は並びを保つ（DD-070-8 の `setData` と同じ決まり）。切れている間に他の参加者が挿した行は「呼んだ後にできた行」
  6. 他の参加者が隠れている行にいるときは、その枠と名前タグを描かない（行の Axis に無いため）
  7. 確かめて壊れたところが共同編集の経路の作り直し（プロトコル・サーバー）を要すると分かったら、そこで止めて単独のみにする判断をユーザーに仰ぐ
- 2026-11-20（確かめの中で決めた細目）:
  8. サーバーの初回の状態を受け取る前に呼んだ `setRowView`（mount の直後・保存していた並びの復元）は、受け取ったメッセージの処理の中で初回の文書から組み立てて反映する（次の描画・次のメッセージより前。待つ間に呼び直したら最後の指定だけ。Codex の指摘で、命令の保留〔`runOrDefer`〕に積む作りから改めた）。受け取る前に組み立てると「呼んだ時点にあった行」が空になり、全部の行が「後からできた行」として文書の並びで見えてしまうため。`visibleRowIds` は受け取る前は `[]`（`getRows` と同じ）
  9. （Codex P1）server は revision 0 でも初期文書が空でなければ bootstrap を送るが、client は welcome の revision だけで「初回の状態を受け取った」と判定していた（DD-070-5 の `getRows` も同じ）。welcome に任意の項目 `bootstrapFollows`（続けて bootstrap を送る）を足し、client はそれを見て待つ。省略は従来の判定（旧 server との互換）。プロトコルの追加は任意の 1 項目だけで、共同編集の経路の作り直しには当たらない（決定 7）

## 受け入れ基準

| # | 基準（操作 → 期待結果） | 検証方法 |
|---|------------------------|---------|
| 1 | A が並べ替えても B の並びは文書の並びのまま。A の Undo・B の Undo は互いに影響しない | E2E（2 クライアント） |
| 2 | A の並べ替え中に B が行を挿す・消す → A では挿した行が一つ前の見えている行のすぐ後に出る・消した行が抜ける。A の選択中の行を B が消したら A の選択は近くの見えている行へ | E2E |
| 3 | A の絞り込み中に B が隠れている行・見えている行の値を変える → 隠れている行は出ず、見えている行は値だけ変わって並びは同じ。A の `getRows` には両方入る | E2E |
| 4 | A の並べ替え中に A の挿入・削除がサーバーに拒否される → 巻き戻った後の並びが決定 4 どおり | E2E（拒否を注入） |
| 5 | A の並べ替え中に切断・再接続（bootstrap）→ 並びが残り、切れている間に B が挿した行は決定 2 の位置に出る | E2E |
| 6 | B が A で隠れている行を選んでいるとき、A に B の枠が描かれない | E2E |
| 7 | mount の直後（初回の状態の前）に呼んだ `setRowView` が、初回の状態を受け取った後に効く（決定 8） | 単体・E2E |

- 工数の判断（親 DD-070）: 共同編集の経路の作り直しは要らなかった（直したのは mount の部品の 1 か所）。両モードで提供する
- 実装をコミット（495e5f4）し、Codex high にレビューを依頼（`DD-070-9/codex-review-result.md`）
- Codex の指摘（10 件・すべて妥当と判断して採用）:
  1. P1: revision 0 で初期文書が空でない文書では、welcome と bootstrap の間に「初回の状態を受け取った」と扱い、空の文書で並びを組み立てていた → welcome に `bootstrapFollows` を足して client が待つ（core の型・codec・server の room・collab の session。決定 9）
  2. P2: 初回の状態の前に予約した古い指定が、受け取った後に呼んだ新しい指定を戻した → 予約は最後の 1 つだけ持ち、受け取った後の指定はすぐ反映する
  3. P2: 受け取った後の次の描画までに届いた他の参加者の挿入まで「呼んだ時点にあった行」に入れて隠した → 初回の状態を受け取ったメッセージの処理の中（`onServerMessageSettled`・lifecycle の `onInitialState`）で組み立てる。行・列の drain の条件にも依らない
  4. P2: 予約した setRowView の後の保留命令（setActiveCell など）が前の並びで動いた → 3 の作りで並びは描画の前に反映され、保留命令は構造の flush の後に drain される
  5. P2: 初回の状態の前は楽観の挿入があると visibleRowIds がその行を返した → 初回の状態の前は `[]`
  6. P2: E2E の後片付けで、画面から推測した行 ID を消すと共有のシード行を消しうる → 挿した行 ID は B の `row-structure-change` の通知から取る
  7. P2: 再接続の E2E は差分の tail しか通らなかった → 切れている間に閾値（1,000 件）を超える操作を作り、snapshot の bootstrap（`bootstrapRevision` が進む）を通すケースを足した。共有の 50,000 行の文書では操作のたびに文書を丸ごと複製する（DD-070-1）ため遅く、小さい文書の認可サーバーで行う
  8. P2: 拒否の E2E がクライアントの実行前の拒否と描かれていない並びでも成功しえた → `permission-denied` だけを数え、並びは描画に使う行の Axis で見る。楽観の並びは挿した同じ処理の中で読む
  9. P2: 在席の枠の E2E の基準が隠れた行を選んだ後に採られていた → A 自身の選択の外に不透明な画素が 0（枠も名前タグも無い）を基準にし、A が B の在席の行を受け取ったことを待つ
  10. P3: B の Undo の深さを A の並べ替えの後に採っていた → 前に採る
- E2E の作りで見つけたこと（本 DD の範囲外・記録だけ）: 1 つのクライアントから 1,000 件超の操作を一度に送ると、未送信が積み上がって接続が「停止」になることがあった（2 回目以降。再接続の扱いに乗る）。E2E は 100 件ずつ ACK を待って送る形にした。通常の操作（貼り付けは 1 つの操作）では起きない
