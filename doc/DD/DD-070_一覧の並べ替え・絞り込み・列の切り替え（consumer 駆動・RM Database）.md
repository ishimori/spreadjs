## 目的

Excel の管理表（RM Database・180 列）を置き換える consumer の一覧・登録画面で、並べ替え・絞り込み・列の表示切り替えと折りたたみ・行から詳細を開く操作・数値の列・下方向へのコピーを使えるようにする。

## 背景・課題

- consumer がこの画面を想定して SDK のコードを確かめ、改良の候補を 8 件出した（2026-11-20・依頼文はユーザー経由）。優先度・高: 列ソート・列フィルタ・列の表示切り替えと列グループの折りたたみ・選択の変更／ダブルクリックの通知。中: 数値の列型・行の追加削除の Undo・フィルハンドル／Ctrl+D・CSV／xlsx の書き出し
- 現状（alpha.23）: `header-click` は通知だけで並べ替えも ▲▼ もない（DD-052-5 が「▲▼ は consumer が描ける」として対象外にしたが、見出しは Canvas に描き `columnCaptions` は mount で決まるので、実際は描けない）。`columnOrder`・`columnGroups`・`columnCaptions` は mount で決まり、React は変えると作り直す。consumer が並べ替えて `setData` すると Undo が消える。選択の変更の通知・Ctrl+D・数値だけを通す列はない
- 設計の手がかり: 画面の行と列の並びは `DocumentView`（`grid/src/document-view.ts`）の Axis 1 か所で文書から組み立て、描画・選択・貼り付けは番号を ID に引き直す。値・Undo・選択の付け替え（`mount/edit-submit.ts` の再ベース）は ID で持つ。並べ替え・絞り込み・列の非表示は、この 1 か所に「見せる並び」を差し込めば、編集の仕組みをほぼそのまま使える

## 決定事項

- 2026-11-20（ユーザー）:
  - 土台は推奨案: SDK は「作り直さずに見え方を切り替える土台」と「通知」を出し、並べ替えの比べ方と絞り込みの候補欄（値を選ぶ UI）は consumer が持つ。見え方は利用者ごとの状態（view-local。文書・Operation・サーバーは変えない。計画書 D-14 と整合。ADR-018 の共有の並べ替え〔D-15〕は将来の別の操作）
  - 一覧のまま編集もできるようにする
  - 単独・共同編集の両モードで作る（共同編集で工数が大きく増えると分かったら、そこで止めて単独のみにする。そのため行の並びは単独〔DD-070-8〕と共同編集〔DD-070-9〕で子DDを分ける）
  - 行数は「大は小を兼ねる」＝5 万行を前提に作る。180 列 × 想定行数は計画書 §21 の性能目標（空でないセル 50 万〜200 万）の外に出うるので、最初に測る
  - 数値の列で「<0.1」「ND」「－」は正しい値ではない → 数値だけを通す列型を SDK に置く
  - 作らない: xlsx の書き出し（README・計画書 §2.5 で対象外）。CSV は consumer が「表のデータを読む API」（DD-070-5）か自分のデータから作る
  - 後回し（次の要望を待つ）: 行の追加・削除の Undo（ADR-0024 の未決事項）・ドラッグのフィルハンドル・SDK に内蔵する候補欄
- 2026-11-20（ユーザー）: 子DDは順に進める。各子DDの実装が終わったら Codex（high）にレビューを依頼し、指摘は妥当性を判断して Claude が直す。都度コミットする

## 計測で分かったこと（DD-070-1）

- スクロールは 900 万セルまで目標の中。メモリは約 420 万セル（180 列で全部埋まり約 2 万 3 千行）まで 300MB に収まる
- **入力確定がセルの数に比例して遅い**（180 列 × 5,000 行で 1 セルの確定に 178ms・11,000 行で 402ms・50,000 行で 0.9〜1.6 秒）。原因は core の `applyOperation` が操作のたびに文書を丸ごと複製すること。単独・共同編集の両モードの確定・貼り付け・Undo・行操作が同じ経路を通る。直す子DD（DD-070-10）を提案中（範囲の追加なのでユーザー判断待ち。判断が出るまでは合意済みの子DDを先に進める）
