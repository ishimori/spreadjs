# ADR-0025: 複数文書 serve の契約と無限 Book への拡張経路

- **Status**: **Proposed**（2026-09-04・consumer 駆動〔松下 DD-014 段3 = 納入計画の共同編集化〕で起票。松下側セッションが DD-043 起票と同時に草稿を代行作成。DD-043 の Human Spec Gate と実装レビューをもって Accepted 判定）
- **関連**: ADR-0005（server-ordered operation log ＝「文書ごとに順序を決める審判は 1 つ」の前提）／ADR-0023（durable 永続化・snapshot＋tail 復元 ＝ 担当引っ越し可能性の基盤）／松下リポ `doc/DD/DD-014/sdk-requirements.md` §D（要件正本）・松下 `doc/decisions.md` D-008（consumer 側の決定: 年度単位の board 切替）

## 背景・課題

- consumer（松下③納入計画）は**年度単位で文書（Book / board）を切り替える**。列構成が年度の日付で決まるため、年が変われば別文書になる（データは DB 側で日付により切り出せる。制約は同期層のみ）
- consumer の将来要望（2026-09-04・明示）: **複数の Excel Book を無限に同時編集**できる仕組みへ育てたい
- 一方、見えている実需は「起動時に分かっている少数の文書」（③の 1〜2 年度・②の 3 シート）。無限の動的部屋管理（遅延作成・idle 後片付け・実行時隔離）を先回りで作ると、使い手のいない高リスク領域を抱える
- よって本 ADR は「**v1 で作る最小の契約**」と「**無限 Book までの拡張経路**」を分けて固定する。DD が倉庫（アーカイブ）へ沈んでも生き残るべき決定はここに置く

## 決定

### 1. 契約は resolver 形式（無限 Book への一本道）

serve へ「documentId → 文書設定（columnOrder / oplog / snapshotStore / initialDocument）」を引く **resolver** を渡す。

- v1 の実装は**起動時の固定リスト**を引くだけ。未知の documentId は拒否する
- 無限 Book 化は resolver の中身を「無ければ作る」に入れ替えるだけで到達し、**公開 API・protocol・既存 consumer を変えない**
- 既存の単一文書指定（現行 ServeOptions）は後方互換で残す

### 2. 接続は文書を名乗る

WS 接続と `/config` は documentId を指定できる。無指定は単一文書構成の既定（後方互換）。

- この documentId は、将来プロセスを複数台に分けたとき、**前段が接続を担当サーバーへ振り分ける routing キー**を兼ねる

### 3. v1 スコープ: N 枚固定 + 起動時の検疫。crash-only は維持

- 動的作成・idle 後片付け・実行時の文書単位隔離は v1 で**作らない**。文書集合の変更はプロセス再起動で行う（クライアントは自動再接続・未 ACK 再送で復帰する。ADR-0023）
- **起動時の検疫**: 復旧に失敗した文書だけを外して diagnostic で大きく警告し、残りの文書で立ち上がる。deterministic poison（特定文書のデータが引き金の復旧失敗）による全文書道連れの再起動ループを防ぐ
- 実行時の恒久失敗（append 恒久失敗等）は現行どおりプロセス fail-stop。文書単位の実行時隔離は、それを要する consumer が現れた時に本 ADR を改訂して設計する

### 4. スケールアウトの想定経路（実装しない・設計制約のみ）

- **文書単位の sharding**: 1 枚の文書を複数サーバーで分担しない（順序の審判は文書ごとに 1 つ ＝ ADR-0005）。文書をサーバーへ振り分ける
- **鉄則「1 文書 1 担当」**: 同一文書を 2 台が同時に受理してはならない（受理順の分岐 ＝ 履歴の分岐）。担当表（v1 は静的設定、将来は期限付きの担当権〔リース〕）で保証する
- **担当の引っ越し**: 全文書の履歴は document_id で仕分けて永続化される（consumer 側 DB 実証済み）。任意のサーバーが snapshot＋tail から任意の文書を立ち上げられるため、fail-over は既存の復旧経路の再利用になる

## 帰結

- v1 の追加面は小さい（resolver・接続の文書指定・起動時の検疫）。既存の単一文書 consumer は無変更で動く
- 無限 Book・複数台化は、resolver の差し替えと前段の振り分けという**外側への追加**で到達できる。本 ADR の契約が変わらない限り consumer の作りは変わらない
- 本 ADR に反する変更（例: 接続から documentId を外す、resolver を固定配列契約に狭める）は、無限 Book への経路を壊すため停止して再判定・ユーザー提示
