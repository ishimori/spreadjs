# ADR-0025: 複数文書 serve の契約と無限 Book への拡張経路

- **Status**: **Accepted**（2026-09-04・consumer 駆動〔松下 DD-014 段3 = 納入計画の共同編集化〕で起票。松下側セッションが DD-043 起票と同時に草稿を代行作成。**DD-043 の実装・全回帰 green をもって Accepted**。実装で確定した細目は下の「実装で確定した細目（DD-043）」に追記）
- **関連**: ADR-0005（server-ordered operation log ＝「文書ごとに順序を決める審判は 1 つ」の前提）／ADR-0023（durable 永続化・snapshot＋tail 復元 ＝ 担当引っ越し可能性の基盤）／松下リポ **アーカイブ済み** `doc/archived/DD/DD-014/sdk-requirements.md` §D（要件正本。松下 DD-014 は 2026-09-04 に完了しアーカイブへ移動した）・松下 `doc/decisions.md` D-008（consumer 側の決定: 年度単位の board 切替）

## 背景・課題

- consumer（松下③納入計画）は**年度単位で文書（Book / board）を切り替える**。列構成が年度の日付で決まるため、年が変われば別文書になる（データは DB 側で日付により切り出せる。制約は同期層のみ）
- consumer の将来要望（2026-09-04・明示）: **複数の Excel Book を無限に同時編集**できる仕組みへ育てたい
- 一方、見えている実需は「起動時に分かっている少数の文書」（③の 1〜2 年度・②の 3 シート）。無限の動的部屋管理（遅延作成・idle 後片付け・実行時隔離）を先回りで作ると、使い手のいない高リスク領域を抱える
- よって本 ADR は「**v1 で作る最小の契約**」と「**無限 Book までの拡張経路**」を分けて固定する。DD が倉庫（アーカイブ）へ沈んでも生き残るべき決定はここに置く

## 決定

### 1. 契約は resolver 形式（無限 Book への一本道）

serve へ「documentId → 文書設定（columnOrder / oplog / snapshotStore / initialDocument）」を引く **resolver** を渡す。

- v1（DD-043）の実装は**起動時の固定リスト**を引くだけ。DD-056-3 で明示的な `addDocument`・`removeDocument` による実行中の登録・撤去を追加した。未登録の documentId は拒否する（接続を受けての遅延作成は行わない）
- 無限 Book 化は resolver の中身を「無ければ作る」に入れ替えるだけで到達し、**公開 API・protocol・既存 consumer を変えない**
- 既存の単一文書指定（現行 ServeOptions）は後方互換で残す

### 2. 接続は文書を名乗る

WS 接続と `/config` は documentId を指定できる。無指定は単一文書構成の既定（後方互換）。

- この documentId は、将来プロセスを複数台に分けたとき、**前段が接続を担当サーバーへ振り分ける routing キー**を兼ねる

### 3. v1 スコープ: N 枚固定 + 起動時の検疫。crash-only は維持

- DD-043 の v1 では文書集合の変更はプロセス再起動で行った。DD-056-3 で consumer が明示的に文書を追加・撤去できるようにした（下記参照）。接続に応じた遅延作成・idle 後片付け・実行時の文書単位隔離は未実装
- **起動時の検疫**: 復旧に失敗した文書だけを外して diagnostic で大きく警告し、残りの文書で立ち上がる。deterministic poison（特定文書のデータが引き金の復旧失敗）による全文書道連れの再起動ループを防ぐ
- 実行時の恒久失敗（append 恒久失敗等）は現行どおりプロセス fail-stop。文書単位の実行時隔離は、それを要する consumer が現れた時に本 ADR を改訂して設計する

### 4. スケールアウトの想定経路（実装しない・設計制約のみ）

- **文書単位の sharding**: 1 枚の文書を複数サーバーで分担しない（順序の審判は文書ごとに 1 つ ＝ ADR-0005）。文書をサーバーへ振り分ける
- **鉄則「1 文書 1 担当」**: 同一文書を 2 台が同時に受理してはならない（受理順の分岐 ＝ 履歴の分岐）。担当表（v1 は静的設定、将来は期限付きの担当権〔リース〕）で保証する
- **担当の引っ越し**: 全文書の履歴は document_id で仕分けて永続化される（consumer 側 DB 実証済み）。任意のサーバーが snapshot＋tail から任意の文書を立ち上げられるため、fail-over は既存の復旧経路の再利用になる

## 帰結

- v1 の追加面は小さい（resolver・接続の文書指定・起動時の検疫）。既存の単一文書 consumer は無変更で動く
- 無限 Book・複数台化は、resolver の差し替えと前段の振り分けという**外側への追加**で到達できる。本 ADR の契約が変わらない限り consumer の作りは変わらない
- 本 ADR に反する変更（例: 接続から documentId を外す、resolver を固定配列契約に狭める）は、無限 Book への経路を壊すため停止して再判定・ユーザー提示

## 実装で確定した細目（DD-043・2026-09-04）

決定 1〜4 は実装でそのまま成立した。実読で追加確定した点だけを残す（DD-043 が倉庫へ沈んでも読めるように）。

- **resolver は「列挙」と対で渡す**: v1 は起動時の検疫（決定3）のために serve する集合を知る必要があるため、
  公開面は `documents = { documentIds, resolve, defaultDocumentId? }`（1 オプション）にした。**無限 Book 化は
  `documentIds` を任意化して `resolve` を遅延呼び出しにする追加**で到達でき、`resolve` の契約・protocol・
  既存 consumer は変わらない（決定1 の一本道は維持）
- **接続の文書指定は query（`?documentId=`）**: handshake frame 方式は upgrade 完了まで宛先 Room が決まらず、
  「どの Room にも属さない接続」の TTL/後始末という新しい状態を作る。query なら upgrade 時点で確定し、
  前段プロキシがそのまま routing キーに使える（決定2 の意図に一致）
- **評価順序は authenticate → 文書解決**: 未認証の相手へ文書集合の存在（未知 ID か否か）を漏らさない。
  文書単位の認可は hook が `request.url` から自分で行える
- **join の申告 documentId 不一致**: 複数文書構成・`?documentId=` 明示の接続では **1008 で切断**する（他文書の
  envelope を oplog へ混ぜない）。従来の単一文書・無指定接続は後方互換のため受理し警告診断のみ（`document-mismatch`）
- **検疫は複数文書構成だけ**: 単一文書構成の復旧失敗は従来どおり起動失敗。1 枚しか無い構成で「0 文書で listen」を
  始めると consumer が起動成功と誤認する。複数文書構成では**全文書が検疫されても listen は続ける**（全接続 404・
  診断 error）。再起動ループを避けるという決定3 の目的は「立ち上がること」自体にあるため
- **`/health` は変えない**（本文 `ok` 固定）。死活監視の口の応答形式を変えるとプローブ側の破壊的変更になる。
  検疫の外形観測は「当該文書への `/config`・`/ws` が 404」＋診断 hook＋`ServerInstance.quarantined` で行う

## 実行中の文書の追加・撤去（DD-056-3・2026-10-12）

- `ServerInstance.addDocument(id, config)` は起動時と同じ検証・復旧・初期文書生成を終えてから登録する。登録済み・処理中・空の ID、停止後、復旧失敗は reject。起動時に検疫した ID を足し直せたら `quarantined` から外す。
- `removeDocument(id)` は登録から外し、受信停止の印を立てて接続を1001で切り、受理済みの永続化・配信・`onAccepted` と実行中の snapshot 生成を待って保存先を閉じる。保存先は消さない。`documentIds`・`quarantined` は読むたびに最新の一覧を返す。
- 外した文書の再接続は404で、未送信の操作は受け付けない。同じ ID・保存先で足し直すと履歴の続きから復旧し、旧クライアントの再送も受け付けるため、別の予算版は別の ID にする。
- 同じ ID への並行処理は拒否し、`stop()` は処理中の追加・撤去を待つ。停止後に復旧を終えた追加は登録せず閉じる。既存の単一文書・複数文書契約と「1文書1担当」は維持する。
- 復旧 callback を呼ぶ前に追加を待機対象へ登録し、文書不一致の診断からの撤去も Room 投入前に再確認する。ストア close が失敗しても両ストアを試し、失敗した文書は remove の再試行・stop の後始末に保持する（同じ ID の追加は後始末完了まで拒否する）。
