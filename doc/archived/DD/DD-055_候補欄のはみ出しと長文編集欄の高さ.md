## 目的

選択式のドロップダウン・日付のカレンダーが枠の下端で切れる不具合（RC16）と、行の高さが上限を超える折り返しセルで編集欄がセルの途中までしか覆わない不具合（RC17）を直し、alpha.10 として配布する。

## 概要

| Bug# | 概要 | 重要度 |
|------|------|--------|
| 1 | 可視域の下端近くのセルで選択式のドロップダウン・日付のカレンダーを開くと、枠より下の部分が切れて候補が選べない（RC16） | HIGH |
| 2 | 行の高さが 128px を超える折り返し（`wrapColumns`）列のセルを編集すると、編集欄がセルの上部 128px だけになり、その下にシートの描画が見える（RC17） | MEDIUM |

- 要件の正本: ready_crew_db `doc/DD/DD-124/sdk-requirements.md` RC16・RC17。乖離したらメモ側が勝つ（DD-035・DD-050・DD-054 と同運用）
- 発見: ReadyCrew の商談進捗シート（本番・0.1.0-alpha.9・Windows Chrome）。最下行の温度感でドロップダウンを開くと候補の2件目以降が枠の下で切れる。先方担当者情報（折り返しで 250px を超える行）を編集すると、編集欄の枠と内部スクロールバーがセルの途中で終わる（2026-09-13 ユーザー報告のスクリーンショット）
- 配布 tarball（alpha.9）の同梱ソースも本DDの原因分析と同じコード（ready_crew_db `node_modules/@nanairo-sheet/grid/src` で確認）
- 公開 API（Facade の options・handle・イベント）は変えない想定。変わる場合は B/C→A 昇格ルールに当たらないか確認してログへ

## 原因分析

### Bug#1: 候補欄が枠の下端で切れる

- `packages/grid/src/select-editor.ts:333-340` `placeListbox()` は常に `top = rect.y + rect.height`（セルの真下）へ置く。下に入りきらないときに上へ開く処理が無い。高さは `maxHeight: 220px`（同 261）
- `packages/grid/src/date-editor.ts:477-483` `placePopover()` も同じ書き方（幅 224px 固定＝同 356）
- 候補欄は stage（`host`）の子で、stage は `overflow: hidden`（`packages/grid/src/dom-scaffold.ts:34`）。枠を越えた部分は描かれない
- 可視域の下端は横スクロールバーの分だけ stage より上にある: `viewportHeight` は `stage.clientHeight`（`mount-controller.ts:639`）、実際に見える本体の高さは `scroller.clientHeight`（同 465 の `ensureActiveCellVisible` が使う値）
- 開いている間は rAF の `refresh()` が毎フレーム同じ `place*()` を呼ぶ（`select-editor.ts:382-385`・`date-editor.ts:513-516`、呼び出し元 `mount-controller.ts:2876-2896`）
- 横方向も `left = rect.x` のままで、右端の列で開くと同じ理由で切れうる（候補は `nowrap`・`minWidth` はセル幅以上）
- 横展開: `packages/grid/src` でセルの下端へ置くポップアップはこの2つだけ（`rect.y + rect.height` の出現は2件。競合 badge はセルの上へ置き 0 でクランプ済み＝`integration-editor.ts:292-293`）

### Bug#2: 長文の編集欄がセルより低くなる

- `packages/grid/src/integration-editor.ts:38` `MAX_WRAP_EDITOR_HEIGHT = 8 * CELL_TEXT_LINE_HEIGHT`（128px）
- 同 200-217 `applyHeight()` は `height = min(max(rect.height, scrollHeight), MAX_WRAP_EDITOR_HEIGHT)`。セル自体が 128px より高いと、セルの高さより上限が優先されて 128px に切り詰まる。内部スクロールの判定（同 216）も `natural > MAX_WRAP_EDITOR_HEIGHT`
- wrap 列は内容に合わせて行が高くなるため、長文ほど条件に当たる。編集中の背景（`EDITING_BACKGROUND`）は textarea の範囲だけなので、下の Canvas の文字がそのまま見える
- DD-052-1 の決定（編集欄を内容に合わせて下へ伸ばし、上限で内部スクロール）は1行の高さのセルを前提にしており、E2E（`apps/playground/e2e/wrap-cell-editing.spec.ts`・DD-052-1 AC4）も低いセルからの伸長だけを見ていた
- 既存の境界: 低いセルでも可視域の下端近くで長文を入力すると、伸びた編集欄が枠の下で切れる（DD-052-1 の仕様どおりの動作だが Bug#1 と同じ種類の見え方）

| # | 論点 | 選択肢 | 推奨と理由 |

## 決定事項

2026-09-13 ユーザー確定（Human Spec Gate・論点1〜5 すべて推奨どおり）:

- 論点1 (a): 下の余白に入りきらず、上の余白のほうが広ければセルの上に開く。高さは開いた側の余白に収め、はみ出す分は内部スクロール。余白の下端は `scroller.clientHeight`（横スクロールバーを除く）、上端は stage の上端（列見出しに重なってよい）
- 論点2 (a): 向きは開いた時点で決め、開いている間は保持する。スクロール・絞り込みでは位置だけ追従し、上向きは候補欄の下端をセルの上端に揃える
- 論点3 (a): 可視域の右端を越えるなら左へずらして収める（左端 0 でクランプ）
- 論点4 (a): 長文の編集欄の上限は `max(セルの高さ, 128px)`。1行の高さのセルの伸び方（DD-052-1 AC4）は変えない
- 論点5 (b): 編集欄が可視域の下端を越えるなら、高さを可視域の下端までに縮めて内部スクロールにする（1行分の高さは下回らない）

## 修正方針

- 候補欄の配置を純関数（例: `computePopupPlacement({ cellRect, popupSize, visibleArea, direction? })` → `{ top, left, direction, maxHeight }`）に切り出し、`select-editor.ts` と `date-editor.ts` の `place*()` から使う。可視域の大きさ（`scroller.clientWidth/clientHeight`）は mount-controller から `open()`／`refresh()` へ渡す
- 編集欄の高さを純関数（例: `computeWrapEditorHeight({ cellTop, cellHeight, contentHeight, visibleBottom })` → `{ height, scroll }`）に切り出し、`applyHeight()` から使う
- どちらも DOM アダプタの薄い変更に留め、IME 状態機械・`ime-editing-session`・focus の保持（I-5）・composition 中に value/selection を書かない規則（I-3）には触れない

## 既知の未保証境界

- 実スクロールバーのある実機ブラウザー（ReadyCrew の Windows Chrome）では確認していない。E2E は headless がスクロールバーを隠すため 16px を模擬した（実装は scroller の client 寸法を読むので、スクロールバーの実幅には依存しない）。実画面での確認は ReadyCrew DD-124 の取り込み時に行う
- 候補欄の横位置は `offsetWidth`（整数に丸めた幅）で計算するため、幅に端数がある候補欄は右端が可視域を 1px 未満越えうる（E2E の右端の選択式ケースで 0.45px）
- 行の高さが可視域より高いセルの編集は E2E で確認していない（入力のたびに走る既存のセル追従と、可視域の下端で縮める処理の組み合わせ）
