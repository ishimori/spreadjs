## 目的

consumer の規則に合わない値を、文書に入る前に止める（DD-060 の案A）。

## 背景・課題

- DD-060 は確定後に印を付ける案B だけを出し、確定そのものを止める案A は「要求が増えたら別DD」とした
- ユーザーが範囲外の対応を指示し、拒否時の動きは「入力を捨てて通知」を選んだ（2026-10-22）。既存の選択式列の候補検証（DD-027-1。確定の関所 `editorSubmit` で未 submit にする）と同じ動きで、IME の状態機械を変えずに済む

## 決定事項

拒否時の動きはユーザーの選択。それ以外はユーザー委任（2026-10-22）により推奨案で確定した。

1. **mount オプション `validateCell?: (cell: { rowId; columnId; value }) => string | null`**（両モード共通・同期）。`value` は確定しようとしている値の表示文字列（cell-commit の `value` と同じ形）。文字列を返すと拒否（その文字列がメッセージ）、`null` なら通す。React は同名 props（関数が変わっても開き直さず、最新の関数を呼ぶ）
2. **拒否したら入力を捨てる**: 文書は変えず（Undo にも積まない）、編集は閉じる（選択式列の候補外と同じ）。新しいイベント `{ type: 'cell-invalid'; source; cells: [{ rowId; columnId; value; message }] }` を**両モード**で出し、診断 `info`（`cell-invalid`）も出す
3. **検証する経路**: IME/textarea の確定（`source: 'edit'`）・選択式の候補の確定（`'select'`）・日付のカレンダーの確定（`'date'`）・貼り付け（`'paste'`）。**貼り付けは1件でも不正なら全体を拒否**し、不正なセルを全部 `cells` に載せる（現行の全成功/全失敗に合わせる）
4. **検証しない経路**: 空にする確定（Delete・範囲クリア・cut・空のまま確定。Excel の入力規則と同じ。必須の確認は申請時に consumer が行う）・Undo/Redo（前の状態へ戻すだけ）・`setRows`／`setData`／リモートの変更（プログラムからの注入・他の参加者の確定）
5. **`validateCell` が例外を投げたら通す**（fail-open）。診断 `error`（`validate-cell-threw`）を出す（consumer の不具合で入力そのものが止まらないように。確定後の検証〔DD-060〕が二段目になる）
6. 読み取り専用・選択式列の候補検証など既存の拒否が先に効く（同じセルを二重に通知しない）

## 既知の未保証境界

- 実 IME（MS-IME）での確定（変換確定→Enter・クリック・blur）で拒否されたあと、次の入力が正常に始まることは未確認（Manual Gate。synthetic composition の経路は E2E で確認済み。拒否の後の扱いは既存の選択式列の候補検証〔DD-027-1〕と同じ経路）
- 拒否したら入力は捨てる（ユーザー決定）。Excel の入力規則のように編集を続けさせることはしない
- `validateCell` は同期関数だけ（サーバーへの問い合わせ等の非同期の検証は、確定後に状態表示〔DD-060/062〕で出す）
- `cell-invalid` は確定処理の後（microtask）に出るため、同期の `subscribe` の中で確定直後の状態を前提にする処理は、届く時点では次の操作が進んでいることがある
