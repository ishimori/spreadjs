# Codexレビュー依頼: DD-070-1（180 列の表の計測）

## 背景

`c:\repo\spreadjs` は業務Webアプリへ組み込むTypeScript製スプレッドシート型入力基盤（Canvas グリッド）。consumer が Excel の管理表（180 列）を置き換えるため、180 列 × 最大 5 万行で性能が計画書 §21 の目標（スクロールの 95% のフレームが 33ms 未満・入力確定 50ms 未満・メモリ 300MB 未満）に収まるかを測る E2E を足した。SDK の実装は変えていない。

DD 本文: `doc/DD/DD-070-1_180列の表の計測.md`（決定事項・計測結果）。

## レビュー対象差分

コミットの `apps/playground/e2e/zz-rm-database-perf.spec.ts`。DD 文書と本依頼書は対象外。

## 決定事項

1. 単独モード（`standalone.html?extracols=176`＝180 列）で、5,000 行・11,000 行（全部埋め・判定する）と 50,000 行（半分埋め・全部埋め・記録だけで判定しない）を測る
2. 測るもの: `setData` から描き終わるまで・縦と横のスクロールのフレーム間隔（p50・p95・最悪）・入力確定の所要・GC の後の JS ヒープ（CDP `HeapProfiler.collectGarbage` → `Performance.getMetrics` の `JSHeapUsedSize`）
3. 判定しないケースで例外が出ても E2E を赤にせず、例外を JSON に記録する

## 評価基準（この観点で見てほしい）

1. **測り方が値をゆがめていないか（最重要）**: 入力データのオブジェクトがヒープの値に残っていないか（evaluate の外へ参照が漏れていないか）、GC の後に測れているか、読み込みの時間の終わり（行数が反映された次のフレーム）が描画の完了を表しているか、スクロールのフレーム間隔の取り方（先頭 2 フレームを捨てる・分位の計算）、入力確定の dispatch が実際の確定の経路を通っているか
2. **ケースの独立**: 各ケースが前のケースの状態（ページ・ヒープ・JSON）に影響されないか
3. **判定の正しさ**: 判定するケースだけを目標で判定し、判定しないケースの失敗を記録して終えているか

## 対象外

- 目標値そのものの当否・ケースの選び方（ユーザーと決めた）
- SDK の実装の性能改善の提案
- 既存の他の E2E

## 出力形式

指摘ごとに「重要度（P1/P2/P3）・ファイルと行・何が起きるか（具体的な条件）・直し方」。指摘が無ければ「指摘なし」と書く。
